## Context

Today an agent working in VortSpec receives three things: `buildIndexDigest`'s flat inventory
(≤200 components, ≤300 tokens, no relationships), a four-field metadata record when one exists, and
— on the compose path — `DESIGN.md` prose cut at `.slice(0, 4000)`. On the light path it receives
`designer.md`: dual-keyed tokens and a framework-free stand-in per component, with strong token
discipline and no guidance whatsoever on which component or variant to reach for.

Two facts drove the shape of this design and are worth restating because they are counter-intuitive:

1. **Storybook is already not in the AI path.** `storybookIndex()` is read only by `RunApp.tsx`. The
   coupling to break is not "Storybook feeds the model" — it is that the *good* metadata schema
   (`.sdd-de/docs/component-metadata-model.md`) is a Storybook deliverable, generated by
   `/storybook`, rendered by `ComponentDocs`, and read by no runtime code. Meanwhile the record that
   does reach the model is a different, thinner schema. Two schemas, neither in the right place.
2. **The relationship layer does not exist at all.** `grep usedBy` across `packages/` returns
   nothing. `InspectorComponent.dependsOn` is the Figma-plan bottom-up build order, has no reverse
   edge, and is not an import graph.

Foundations already in place and reused rather than rebuilt: the B2 scan cache, the durable
`.vortspec/maps/` join tables, `buildIndexDigest`'s bounding and `safePromptField` sanitation, and
`buildDesignAudit`'s finding model.

Constraint from `docs/agentic-design-system-plan.md` §1.6: the published benchmark for this
architecture holds token cost flat (+3.5%) while accuracy goes 65% → 100%. That is the bar. A design
that makes runs materially more expensive has missed the point.

## Goals / Non-Goals

**Goals:**
- One metadata schema, owned by VortSpec, read by every consumer including Storybook.
- A relationship graph and honest adoption measurement, built in-process.
- Rules that make an agent navigate rather than explore.
- Governance that catches a valid token in the wrong place.
- Roughly flat interactive token cost; new spend confined to background reports.

**Non-Goals:**
- Not a multi-agent system. The series describes one agent over good infrastructure, and so does
  this. No orchestration layer, no agent handoffs.
- Not embeddings or a vector store. Static analysis over a known component set is deterministic and
  auditable; retrieval-by-similarity is neither.
- Not AST parsing in v1. Regex-and-profile scanning over the existing cache is what the scan cache
  already does and is sufficient for imports and tag counting.
- Not removing Storybook, `DESIGN.md`, or the token views. All three stay as human surfaces.
- Not touching a consumed library's source. Consume-source projects report findings and route
  corrections to the durable overlay.

## Decisions

**Store metadata at `.vortspec/metadata/*.json`, not co-located `<Name>.metadata.ts`.**
The series co-locates a TypeScript module next to each component. VortSpec cannot: for a consume
source the component tree belongs to the client and is never written, and the existing
`.vortspec/`-owned convention already encodes that boundary. JSON also parses without a build step,
which matters because the main process reads these records. *Alternative considered:* co-located
modules, matching the articles exactly — rejected because it breaks on consume sources and requires
transpilation to read.

**Widen the existing schema; do not introduce a second one.**
`componentMetadataSchema` grows from four fields to nine sections, with the legacy fields mapped on
read. The alternative — a new `aiMetadataSchema` alongside the old — would recreate the exact fork
this change exists to close.

**Migration is read-time and lossy-by-declaration.**
A legacy record migrates in memory (`summary` → `identity.description`, `usage[]` →
`usage.useCases`, `patterns[]` → `usage.commonPatterns`, `antiPatterns[]` → triplets with empty
`reason`/`alternative`) and is reported *incomplete*. It is not silently upgraded on disk: a triplet
with two empty fields is not equivalent to an authored one, and marking it complete would hide the
regeneration that is actually needed. *Alternative considered:* a one-shot rewrite migration —
rejected because it would manufacture false completeness.

**Build the index in TypeScript, not by shelling out to the vendored Python skill.**
`codebase-index` ships a Python script and is already vendored. Shipping an Electron app that
requires a Python interpreter at runtime is a support burden out of proportion to the work, and the
scan cache already holds the file set. The Python script stays as a reference implementation for the
counting semantics. *Alternative considered:* bundling a Python runtime — rejected on install size
and platform risk.

**Key on full project-relative path; count instances, not imports.**
Both are documented bugs from the series (§1.2 of the plan) and both are cheap to get right up
front: stem-keying silently overwrites entries for any two files sharing a basename, and
import-counting reports a component as adopted when it is imported and never rendered. Slot-nested
instances are de-duplicated — the series attributes a 75% → 95% accuracy jump to exactly this.

**TOON on disk, existing compact format in the prompt.**
The artifacts under `.vortspec/ai/` are TOON, matching the series and its token claim, and are
committed so they are reviewable in a diff. The in-prompt digest keeps `buildIndexDigest`'s current
format, which is already compact and already sanitized — reformatting it would risk the bounding and
injection guarantees for a marginal saving. *Alternative considered:* TOON end to end — rejected
because the digest's safety properties are worth more than the bytes.

**Relationships enter the digest bounded, with on-demand expansion.**
The full graph is not prepended. The digest gains a bounded relationship section; a run that needs
one component's `uses`/`usedBy` requests it. This is what keeps the cost claim honest on large
systems.

**Governance rules are data, evaluated by the audit; the LLM is the fallback, not the mechanism.**
Hierarchy, elevation, semantic-color and typography-composite rules are declarative records under
`.vortspec/ai/governance/`. Where a rule is mechanically checkable against the token graph
(`design-tokens.toon` plus resolved values) it is checked deterministically. Only genuinely
judgment-bound cases go to a model. *Alternative considered:* an LLM pass over every component,
which is how the series describes v2 — rejected as the default because it is non-deterministic and
recurring; it stays available for the residue.

**Reports are background work on the cheapest capable model.**
Adoption and violation reports are off the interactive path and routed to Haiku, consistent with
existing verify/Apply routing. The series reports ~$0.20 per comprehensive report; that is the
target order of magnitude.

**The light path gets hints in `designer.md`, not a second file.**
`LiteComponent` gains a compact `hints` block serialized into the manifest frontmatter. It must
survive `findFrameworkPointers`, so hints carry no import paths, no module aliases and no
`.tsx`/`.variants.ts` references — selection criteria, variant purposes and anti-pattern scenarios
are prose about intent, which is naturally framework-free. Serialization already throws on a leak;
that guard is the enforcement.

**Storybook becomes a reader in the same change that widens the schema.**
Splitting them would leave a window where `ComponentDocs` reads a module that generation has stopped
writing. `/storybook` and `ComponentDocs` are switched to the JSON store as part of group 1.

## Risks / Trade-offs

**Instance counting is the hardest part and the easiest to get quietly wrong** → Build it
test-first against fixtures covering slots, conditionals, loops, and multi-level composition, with
the expected counts asserted. A wrong count is worse than no count because it launders a guess as a
measurement.

**Shadow-implementation detection will produce false positives** → Ship it as a `warning`, never an
`error`, and require the finding to name both the shadowed component and the file so a human can
dismiss it in one look. A structural heuristic that blocks a build would be rejected outright.

**Widening the metadata schema raises the cost of generating a record** → Generation is a
mechanical transform of the Component/Interaction Specs, not a fresh analysis, so most sections come
from data the project already has. Only `aiHints`, `commonPatterns` and `antiPatterns` need
analysis. Generation stays a background, gated run.

**The digest could grow past its bound as systems scale** → The bound is explicit and truncation is
stated in the digest rather than silent; the on-demand relationship lookup is the pressure valve.
Regression-test the digest size against a large fixture.

**`designer.md` is owned by an unarchived change (`light-design-system`, delta
`lite-design-manifest`)** → The hints block is additive and optional. Components without metadata
serialize exactly as they do today, so the two changes can land in either order.

**Committing generated TOON artifacts creates diff noise** → Accepted deliberately: a reviewable
diff of what the agent will read is the point, and it is what makes staleness visible in code review
rather than only in CI.

**Intent rules encode opinions that may not be this project's opinions** → Rules are per-project
data under `.vortspec/ai/governance/`, seeded with defaults and editable. A rule the team disagrees
with is deleted, not worked around.

## Migration Plan

1. Widen the schema with read-time migration; existing four-field records keep loading and are
   reported incomplete. No disk rewrite.
2. Switch `/storybook` and `ComponentDocs` to the JSON store in the same group; stop authoring
   `<Name>.metadata.ts`. Existing `<Name>.metadata.ts` files are left on disk, unread — deleting
   them is the user's call, not a side effect of an upgrade.
3. Build the index; it is additive and absent until first built. Every consumer degrades to today's
   behavior when `.vortspec/ai/` does not exist.
4. Rules, governance and reports are additive artifacts with no removal step.

**Rollback:** each group is independently revertible. Reverting group 1 leaves the widened records
readable by the old four-field parser only for the fields it knows, so a rollback past group 1
should be paired with regenerating records — noted rather than automated, because the situation is
unlikely and the automation would be more dangerous than the manual step.

## Open Questions

- Does the elevation rule need a project-configurable scale, or is the token file's shadow scale
  always sufficient to derive it?
- Should the AI-readiness level be recomputed on every index build, or only on demand? Recomputing
  is cheap, but a level that moves without an explicit action may read as noise.
- For consume sources, is shadow-implementation detection meaningful against a vendor library the
  team cannot change, or should it be limited to the team's own application code?
