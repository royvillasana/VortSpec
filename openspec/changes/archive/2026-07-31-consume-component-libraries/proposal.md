## Why

When a project's design source is an existing component library, VortSpec should **consume the library's real components** — not re-create look-alikes. Today the `library` source *intends* to consume but structurally rebuilds: its provisioning prompt defers to a `/provision-library` skill that **does not exist on disk** (`sdd-prompts.ts:103`), "provisioned" is a **component-count proxy** (`libraryProvisioned = !isLibrary || total > 0`, `GuidedFlow.tsx:486`), and the auto-builder excludes **only** `enterprise` (`useAutoComponentBuild.ts:65-71`) — so a library project's real components get swept into the from-scratch `buildChunkPrompt` cycle and reimplemented as CVA+token+test look-alikes that drift from the library. The one fully-wired consume path is `enterprise` (validate → pointer-index → embed the client's own Storybook → swap-at-generate); it is the working template. This change generalizes that consume model to all component-library sources, stops rebuilding what a library already ships, drops the redundant Storybook build for consumed libraries, and adds **Astryx (Meta)** as a first-class library source.

## What Changes

- **Consume by library type, never rebuild.** Introduce a taxonomy and a consume mechanism per type:
  - **CLI-registry** (shadcn/ui, and shadcn-compatible registries) — run the library's real CLI non-interactively (`npx shadcn@latest add --yes <items>`), copying the real source into the repo; enumerate props/variants from the copied CVA `variants` maps.
  - **Installed-package** (MUI, Chakra, Mantine, Ant Design, **Astryx**) — `npm install` and import from the package; enumerate props/variants from bundled `.d.ts` (react-docgen-typescript) or the vendor's docs/MCP; never copy source; at most a thin token-mapped wrapper per primitive.
  - **Headless** (Radix, React Aria) — install + import; note they carry **no token model** and must be paired with the project's tokens.
  - **CSS-in-JS styling** (Emotion, styled-components) — explicitly **not** a component source; recognized as a `styling` strategy, never offered as a library to consume.
- **Enforce consume over rebuild.** Extend the auto-builder's `enterprise` exclusion to **all consume sources** so consumed components are never pushed through `buildChunkPrompt`; replace the count-proxy readiness gate with a **real readiness check** (did the CLI run / does the package resolve / are there pointer entries), mirroring `analyzeEnterpriseReadiness` (`enterprise-consume.ts:64-108`).
- **Author the missing consume skill.** Create `.sdd-de/ai-specs/skills/provision-library/SKILL.md` (referenced by `PROVISION_LIBRARY_PROMPT` but absent), encoding the per-type recipes; or make the prompt self-contained.
- **Pointer-shaped inventory.** For consume sources, `.sdd-de/components.json` entries carry an `importPath`/`export`/`storyId` pointer (mirroring `EnterpriseComponentEntry`, `enterprise-consume.ts:29-40`) instead of the rebuild-oriented `{name, level, figmaNodeId}` shape.
- **Skip Storybook; show the library's design system instead.** For consume sources, do **not** install/build a VortSpec Storybook. Surface the design system via the existing palette screen (`DesignSystem.tsx`, reads only tokens + `components.json` + stand-ins) and/or the vendor's **own** embedded Storybook/docs (generalizing `resolveEnterpriseStorybookUrl`). Make `/storybook` and `/design-doc` **not** prerequisites for consume sources.
- **DESIGN.md points at consumed code.** DESIGN.md's `## Components` emits the pointer import path + the vendor's docs URL (not `localhost:6006`), and `/design-doc` becomes optional for consume sources — the pointer index + tokens are enough to ground composition.
- **Add Astryx (Meta)** to the library options, classified as **installed-package** (`@astryxdesign/core` + `@astryxdesign/theme-neutral` + `@astryxdesign/cli`; `npx @astryxdesign/cli init` generates agent docs; StyleX-based token vars). Setup SHALL **verify the packages resolve** (research could not independently confirm them via npm) and read the installed `package.json` / run the library's doctor before wiring — never hard-code CLI/MCP/version specifics.
- **Concrete per-library consume recipes** — encode the exact install / import / theming-artifact / per-component-override / API-enumeration for shadcn, MUI, Chakra, Mantine, Ant Design, Radix, and Astryx (two camps: *copy-into-repo* source-owned vs *node_modules* config-owned), so consuming is deterministic per library rather than a generic prompt.
- **Personalize any component's design system per project (customization).** A user SHALL be able to edit the design tokens / theme of a project — from VortSpec's existing token editor — and have it re-theme the components **regardless of how they entered VortSpec** (built, light-page, enterprise-consumed, library-consumed, draw-to-component). Tokens are the single source of truth; a durable per-project **override overlay** (global by token name, per-component by `data-component`) is **materialized per source**: CSS variables (shadcn / built / Astryx / MUI css-vars), a generated/patched **theme config** (MUI `createTheme`, Chakra `defineConfig`, Mantine `createTheme`, Antd `ConfigProvider`), or a VortSpec-owned **overlay resolved on top** for enterprise (never modifying the client's real source). This requires a **multi-format token writer** (today only CSS `--name:` writes succeed; a JS/TS theme-object `token_file` silently no-ops) and a **durable override + materializer layer**.
- **Detection at intake** — inspect the target repo (`components.json` present → CLI-registry; UI package in deps → installed-package/headless; only `@emotion/*`/`styled-components` → styling, not a component source) to auto-suggest the kind.
- **BREAKING (behavioral):** a `library` project no longer hand-builds the library's components; it consumes and (optionally) thin-wraps them. Existing library projects are unaffected until re-provisioned.

## Capabilities

### New Capabilities
- `library-consumption`: Consume an existing component library as the design source per its type (CLI-registry / installed-package / headless), running the real CLI or installing the package, enumerating the library's real props/variants for AI grounding, writing a pointer-shaped inventory, and **enforcing** that consumed components are never rebuilt. Includes intake detection, the per-type consume skill, per-library recipes, and Astryx (Meta) as a concrete installed-package source.
- `component-token-customization`: Personalize a project's design system by editing tokens/theme from VortSpec's existing token editor, applied to **any** component regardless of source (built / light-page / enterprise / library-consumed / draw-to-component). A durable per-project override overlay (keyed globally by token name, per-component by `data-component`) is materialized per source — CSS variables, a generated theme config, or a read-only overlay for enterprise — backed by a multi-format token writer.

### Modified Capabilities
- `design-input`: The design-source contract gains a **consume outcome** for component libraries — selecting a library at setup SHALL result in the library's real components being consumable (source copied for CLI-registry; package installed + importable for installed-package/headless), parallel to how Figma/ZIP/GitHub land their source of truth. (Supersedes/absorbs the in-flight `provision-library-source` change, which covered provisioning but not the readiness, no-rebuild enforcement, Storybook-skip, DESIGN.md, or Astryx scope.)
- `design-system-readiness`: Library readiness SHALL be a real check (CLI ran / package resolves / pointer entries exist), replacing the `total > 0` component-count proxy; consume sources SHALL be excluded from auto-build.
- `storybook-consumption`: The "skip a VortSpec-built Storybook; display the source's own design system" behavior currently scoped to `enterprise` SHALL extend to **all** consume-source component libraries — via the palette screen and/or the vendor's embedded Storybook — and `/storybook` SHALL NOT be a prerequisite for them.
- `design-manifest`: For consume sources, DESIGN.md SHALL reference consumed code (pointer import paths + vendor docs URLs) rather than local `component_dir` source + `localhost:6006` Storybook URLs, and `/design-doc` SHALL be optional.

## Impact

- **Toolkit skills** (`.sdd-de/ai-specs/skills/`): new `provision-library/SKILL.md`; `setup/SKILL.md` (kind detection + Astryx + richer library descriptor); `extract-design-system/SKILL.md` (pointer inventory for consume sources); `storybook/SKILL.md` and `design-doc/SKILL.md` (skip/optional + consumed-code references); `CLAUDE.md` (relax the Path B `/storybook`+`/design-doc` gate for consume sources; document the consume-vs-rebuild source families).
- **VortSpec core/UI**: `packages/core/src/shared/setup.ts` (broaden `component_library_kind` → cli-registry/installed-package/headless; add `library_registry`/`library_install_cmd`/`library_add_cmd`/`library_import_base`/`library_mcp`; add Astryx); `sdd-prompts.ts` (`PROVISION_LIBRARY_PROMPT`, `DESIGN_REFERENCE_CLAUSE` consume branch, pointer-inventory rescan writer); `packages/ui/src/lib/useAutoFoundation.ts` + `useAutoComponentBuild.ts` (generalize the `enterprise` branch to `isConsumeSource`); `packages/ui/src/views/GuidedFlow.tsx` (real readiness gate + consume affordance); `DesignManifest.tsx` (`GENERATE_PROMPT` consume branch); `RunApp.tsx`/`DesignSystem.tsx` (display path).
- **Config**: `project.yaml` gains the richer library descriptor + a `theme_apply` strategy; `components.json` becomes pointer-shaped for consume sources; a new durable `.vortspec/theme-overrides.json` holds the per-project override map.
- **Customization layer**: the token writer/reader in `packages/core` (`inspector/token-parser.ts` — `setInspectorTokenValue`/`replaceDecl` currently CSS-only; `getInspectorTokens` the single reader) gains multi-format writing + a durable override overlay; a **materializer** (generalizing `light-serve.ts:injectTokens`) applies overrides per source as CSS vars / a generated theme config / an Astryx `defineTheme` / an enterprise overlay; the token↔library-theme-key mapping joins the existing token resolver; the inspector/`visual-token-editing` UI stays the single edit surface.
- **Astryx**: exact CLI subcommands, MCP registration, theme/component counts, and package versions are **unconfirmed** in research — resolved at intake via CLI/MCP or confirmed with the user; not hard-coded (see design.md open questions).
- **Constraint preserved**: VortSpec runs the library's CLI / installs packages through the user's own local toolchain (npm/npx) — it never vendors, proxies, or reimplements the libraries; and it never calls Figma directly.
