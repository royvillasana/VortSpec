# The Agentic Design System — review, gap analysis, and implementation plan

**Sources reviewed:** the six-part *Agentic Design Systems* series by Cristián Morales (Design Systems
Collective, Parts 1–6) and the companion FigJam board *How to Build an Agentic Design System*
(`figma.com/board/zilsOCRmQ0EBmqwIRXe3ET`).

**Verified against:** the VortSpec codebase as of `openspec/live-playground` @ `3391cf7e`.

---

## Part 1 — What the series actually prescribes

Strip the prose and the series describes one thing: **a RAG pipeline for a design system**, where the
retrieval corpus is not documentation but *generated structured data*, and the agent is taught how to
query it. The author calls the operating model **ARC** — Audit → Report → Compose.

### 1.1 Three layers of infrastructure

| Layer | Question it answers | Artifact | Owner |
|---|---|---|---|
| **1. Codebase index** | *What exists and where* | `index.toon`, `component-usage.toon`, `design-tokens.toon` under `.ai/` | generated by script |
| **2. Component metadata** | *How and why to use it* | `<Name>.metadata.ts` co-located with each component | generated by skill, human-curated |
| **3. Query protocols** | *How to read layers 1–2* | `CLAUDE.md` + `.claude/rules/*.md` | hand-authored, project-specific |

The board splits layer 3 further into **Skills** (executable, portable across projects), **Rules**
(passive constraints, project-specific — the metadata schema, the atomic hierarchy, the tracing
methodology), and **Instructions** (the strategy that binds them: *when* to load the index, *how* to
approach a query class, *what* artifacts to produce and where they feed).

### 1.2 The index (Part 4 — *Codebase indexing*)

Static analysis, **not** AST parsing and **not** embeddings. Three outputs:

- **Inventory** — every component: name, category, path, whether it has metadata.
- **Relationship graph** — `uses` / `usedBy` import chains, followed *recursively* (Page → Layout →
  Nav → Link), so "which atoms does this page use" is answerable without reading the page.
- **Summary statistics** — total counts, metadata coverage, relationship density.

Serialized in **TOON** (Token-Optimized Object Notation), claimed 30–60% smaller than JSON:

```
Button:
  path: src/components/atoms/Button
  category: atoms
  metadata: true

ThoughtCard:
  uses[0]:
  usedBy[2]: ThoughtsSection, [slug].astro
```

Two details that matter and are easy to get wrong — both are bugs the author hit and documented:

1. **Key on the full relative path, not the filename stem.** `src/pages/index.astro` and
   `src/pages/skills/index.astro` both stem to `index` and the second silently overwrites the first.
2. **Import count ≠ instance count.** Adoption is measured by counting component *tags* in template
   bodies, multiplied through composition levels, with slot-nested instances de-duplicated. Getting
   slot detection right moved their accuracy from 75% → 95%+.

The index is **committed alongside the code** and regenerated after component changes. Freshness is a
CI concern the author explicitly flags as unbuilt.

### 1.3 The metadata (Part 3 — *Documentation as structured metadata*)

The core argument: Storybook and MDX encode design decisions **in prose that requires inference**.
"Avoid multiple primary buttons" is a sentence a human resolves from context; an agent needs it as a
queryable record. Crucially the author frames this as a **translation layer, not a replacement** —
human docs stay exactly as they are.

Nine sections, split by purpose:

**Critical for decision-making**
1. `usage` — `useCases[]`, `commonPatterns[]` (name/description/composition), and `antiPatterns[]` as a
   strict **scenario / reason / alternative triplet**
2. `aiHints` — `priority`, `keywords[]`, `selectionCriteria{}` (one clause per variant)
3. `variants` — `options[]`, `default`, and a `purpose{}` map explaining *what each variant is for*
4. `composition` — slots, nested components, parent constraints
5. `behavior` — states, interactions, responsive considerations

**Completeness**
6. `props` · 7. `accessibility` (role, keyboardSupport, screenReader, wcag, notes[]) · 8. `examples`

**Reference**
9. `component` — name, category, description, type, path, timestamps

The structural insight worth stealing: **discovery is separated from intent**. An agent scans only the
`component` headers across the whole library to shortlist candidates, then reads full metadata for the
two or three that survive. That is what keeps it affordable at library scale.

The anti-pattern triplet is a forcing function — you cannot write it vaguely.

### 1.4 Governance (Part 6 — *Encoding governance*)

The pivot from **v1 existence checking** to **v2 intent checking**:

- **v1** — scan CSS for `var(--*)` and assert each name exists in the token source. Catches hardcoded
  values and typos. This is find-and-replace with extra steps.
- **v2** — reason against *encoded design decisions*: visual hierarchy, foreground sequence, elevation-
  to-size coherence, semantic color model, typography composites. Catches `--foreground-muted` used for
  body copy: the token exists, the reference is syntactically perfect, and it is **the wrong position in
  the hierarchy**.

On identical files: **v1 found 43 violations, v2 found 64** — the extra 21 were all relationship
violations where every individual token was legal but misapplied in context.

The board names the deliverable: `reports/token violations by component`, produced by a
`token-auditor v2.1.0` skill.

### 1.5 Orchestration (Part 5) and the operating model (Part 2)

Notably, this is **a single agent over good infrastructure**, not a multi-agent swarm. The routing
hierarchy is `CLAUDE.md (router) → Rules → Skills → Artifacts`. Load the index once per conversation
(~4,000 tokens); never re-read a relationship file already in context.

ARC in practice:

- **Audit** (consumer) — query the index for inventory and location. No file traversal.
- **Report** (maintainer) — adoption reports, technical debt, shadow implementations. ~$0.20 a run.
- **Compose** (self-governing) — detect drift from the contracts encoded in metadata, generate fixes.

### 1.6 The benchmark

11 trials on an Astro portfolio, four fixed questions, control (no index, no `CLAUDE.md`) vs. agentic:

| Metric | Without | With | Δ |
|---|---|---|---|
| Accuracy | 65% | 100% | +54% |
| Speed | 4:26 | 1:52 | 58% faster |
| Component discovery | 77% | 100% | 13 more found |
| Run-to-run variance | 26.5% | 0.04% | 99.9% more reliable |
| False negatives | 60% | 0% | eliminated |
| Token cost | 27,211 | 28,166 | +3.5% |

#### The four questions (recovered from the board, Frame 184)

The plan referenced "the four fixed questions" without ever recording them, which made tasks 2.10
and 3.8 unexecutable. They are, asked IN SEQUENCE in one session:

| # | Question (as run on the board's Astro repo) | ARC phase | What it exercises |
|---|---|---|---|
| Q1 | "How many components do we have on this repo?" | Audit | Query the index for a complete inventory |
| Q2 | "List all components used on `index.astro`" | Report | Read the relationship graph, generate a specification |
| Q3 | "List all atoms used on that page" | Compose | Reason over cached data, filter by category |
| Q4 | "How many of these components are being used on other pages?" | Compose | Traverse pre-computed `usedBy` |

**They are sequential, not independent.** Q3 says "that page" and Q4 says "these components" — each
depends on the previous answer. The board tested this deliberately, listing "session pollution,
sequential queries, accumulated context" as the real conditions the infrastructure had to survive.
Running the four as separate sessions would measure something easier than what was claimed.

**Q2 must be parameterized to stay framework-agnostic.** `index.astro` is the board's own repo, not a
property of the method. VortSpec supports nine frameworks and Astro is one of them, so a literal
`index.astro` would make the benchmark unrunnable on eight of the nine. The question is really "list
the components used on the project's main entry page"; the entry page resolves per framework
(`src/pages/index.astro`, `app/page.tsx`, `src/App.tsx`, …), which `FRAMEWORK_PROFILES` already knows
how to find. Q3 and Q4 then chain off whatever Q2 resolved.

**Control vs agentic setup.** Control: no `.vortspec/ai/` artifacts, no `CLAUDE.md`, discovery by
filesystem traversal. Agentic: pre-generated TOON index, relationship graph, and the project
instructions that tell the agent to query rather than explore.

**The token cost is flat.** The infrastructure does not buy cheaper runs — it converts token spend
*from exploration into analysis*. That is the whole thesis, and it is the number to keep in mind when
weighing this against the cost/token-optimization priority: this is not a spend increase, it is a
spend reallocation with a large accuracy return.

### 1.7 The AI-readiness maturity ladder (board, Frame 234)

Worth adopting verbatim as a product surface — it is a scoreboard VortSpec could compute:

1. **Libraries** — components and tokens exist, structure inconsistent → AI approximates.
2. **Standardised** — clear naming, logical token hierarchy → AI can reference structure.
3. **Governed** — ownership, versioning, decision rationale captured → AI can flag violations.
4. **Operational** — deterministic tokens, explicit states, machine-readable docs, API-like access →
   AI can generate, refactor and validate against the *real* system.
5. **Agentic** — governance logic invocable, workflows observable, toolchains integrated → AI
   participates as a constrained collaborator.

## Part 2 — What VortSpec does today

VortSpec is further along than the framing "we use Storybook as AI context" suggests — but the pieces
are split across two disconnected schemas and the graph layer is missing entirely.

### 2.1 Storybook is already not the AI context

`storybookIndex()` is consumed only by `packages/ui/src/views/RunApp.tsx` (lines 1052, 2523) — the
Playground's human-facing embed. No prompt builder reads it. The premise "we feed Storybook to the AI"
is **not what the code does**.

The real coupling is subtler and worse: **the rich metadata is a Storybook deliverable.**
`.sdd-de/docs/component-metadata-model.md` defines a genuinely good schema — `identity`, `props`,
`itemShape`, `designTokens` (with resolved values), `states`, `accessibility`, `commonPatterns`,
`antiPatterns`, `aiHints` — and it is close to the article's nine sections. But:

- it is **generated by `/storybook`**, so no Storybook ⇒ no metadata;
- it is **rendered by `.storybook/ComponentDocs`**, so its consumer is a docs page;
- and `grep` confirms **nothing in `packages/core` or `packages/ui` ever reads a `<Name>.metadata.ts`.**
  The only mention is `compose-run.ts:224`, which *instructs an agent to write one*.

### 2.2 The runtime AI context is a different, thinner thing

| Artifact | Where | What it carries |
|---|---|---|
| `buildIndexDigest()` | `main/inspector/index-digest.ts` | flat inventory, ≤200 components + ≤300 tokens, prepended to every grounded run. Sanitized, bounded, sourced from the scan cache. **No relationships.** |
| `.vortspec/metadata/<name>.json` | `main/inspector/component-metadata.ts` | four fields: `name`, `summary`, `usage[]`, `patterns[]`, `antiPatterns[]` — all free-text string arrays (schema: `shared/inspector.ts:465`) |
| `designer.md` | `shared/lite-manifest.ts` | dual-keyed tokens + a framework-free HTML stand-in per component. Tiers, variants, props, readiness. **No usage, no anti-patterns, no aiHints.** |
| `DESIGN.md` | via `compose-run.ts:295` | prose hand-off, **truncated with `.slice(0, 4000)`** |
| `.vortspec/maps/tokens.json` | `main/inspector/design-map.ts` | durable code-token → Figma `variableKey` join table |
| `buildDesignAudit()` | `main/inspector/design-audit.ts` | two rules: `hardcoded-color`, `token-drift` |

So there are **two metadata schemas that do not know about each other**: a rich one that exists to
render Storybook docs, and a thin one that actually reaches the model.

### 2.3 What is genuinely missing

- **No relationship graph.** `grep usedBy` returns nothing. `InspectorComponent.dependsOn` exists but is
  the Figma-plan bottom-up build order, not an import graph, and there is no reverse edge.
- **No consumption measurement.** No import counts, no instance counts, no efficiency ratio, no shadow-
  implementation detection, no adoption report. Nothing can answer "is this component actually used?"
- **No query protocol layer.** `ai-ds-composer`, `ai-component-metadata` and `codebase-index` are all
  already vendored under `.sdd-de/ai-specs/skills/` — the author's own skills, installed and **not wired
  into any VortSpec run**. There are no rules teaching deep tracing or load-once discipline.
- **Governance is v1 only.** Hex-literal detection and Figma drift. No intent checking.
- **The light path — where VortSpec's AI generation actually happens — is the least informed.**
  `buildLightPagePrompt` hands the model `designer.md` plus the stand-ins. It enforces token discipline
  well (the dual-key `var(--x, #val)` rule is genuinely strong) but the model gets **zero signal about
  when to choose which component or which variant, and zero anti-patterns.** That is precisely the gap
  the article's `aiHints.selectionCriteria` and `variants.purpose` exist to close.

### 2.4 Gap summary

| Article layer | VortSpec today | Gap |
|---|---|---|
| Index — inventory | `buildIndexDigest` | ✅ present, bounded, sanitized |
| Index — relationship graph | — | ❌ missing entirely |
| Index — instance counts / adoption | — | ❌ missing entirely |
| Index — TOON serialization | custom compact text | ◐ fine for the digest; needed for on-disk artifacts |
| Metadata — 9-section schema | two rival schemas, neither read at runtime | ◐ rich one is Storybook-only, thin one is 4 fields |
| Metadata — variant `purpose` / `selectionCriteria` | — | ❌ the highest-value missing field |
| Metadata — anti-pattern triplet | free-text strings | ◐ unstructured |
| Query protocols / rules | skills vendored, unwired | ❌ not reachable from a run |
| Governance v1 | `buildDesignAudit` | ✅ present |
| Governance v2 (intent) | — | ❌ missing |
| Adoption reporting | — | ❌ missing |
| AI-readiness score | `design-system-readiness` spec exists | ◐ different axis; no maturity ladder |
| Human validation surface | Storybook + Design System view | ✅ already correct — keep it |

**On the premise:** you are right that the AI's information model should not be Storybook-shaped, and
right that Storybook should stay for human validation. The correction is that Storybook is not
currently *in* the AI path — it is *upstream of* the artifact that should be. The fix is to **invert
ownership**: make the structured metadata a first-class VortSpec artifact, and make Storybook (and the
Design System view, and `ComponentDocs`) *readers* of it.

## Part 3 — Implementation plan

Five groups. Each is independently shippable and each is verifiable by the benchmark protocol in §1.6.

### Group 1 — One metadata schema, VortSpec-owned

**Goal:** kill the fork. One schema, written and read by VortSpec, rendered by Storybook.

- Widen `componentMetadataSchema` (`shared/inspector.ts`) from four fields to the nine sections, keeping
  every existing field so nothing breaks:
  - `identity` (from the current `name` + `summary`) — add `type`, `importPath`, `figmaFile`,
    `figmaNode`, `generatedAt`
  - `usage.useCases[]`, `usage.commonPatterns[]{name,description,code}`,
    `usage.antiPatterns[]{scenario,reason,alternative}` ← **triplet, not free text**
  - `variants{}` — per axis: `options[]`, `default`, **`purpose{}`**
  - `aiHints` — `priority`, `keywords[]`, **`selectionCriteria{}`**
  - `composition` — `slots[]`, `nests[]`, `parentConstraints[]`
  - `behavior` — `states[]`, `interactions[]`, `responsive[]`
  - `props[]`, `accessibility{}`, `designTokens{}` (resolved values, as today)
- Keep the store at `.vortspec/metadata/<name>.json` — VortSpec-owned, never the app's source. Migrate
  the four legacy fields on read so existing files stay valid.
- Rewrite `buildMetadataPrompt` to fill the new schema, sourcing from the Component/Interaction Specs
  the way `component-metadata-model.md` already prescribes (it is a mechanical transform, not a fresh
  analysis) and from `ai-component-metadata`'s analysis fields for the rest.
- **Retire `<Name>.metadata.ts` as an authored artifact.** Change `/storybook` and `ComponentDocs` to
  *read* `.vortspec/metadata/*.json`. Update `.sdd-de/docs/component-metadata-model.md` to describe the
  new ownership. Storybook becomes a view, which is what you asked for.

*Verify:* `ComponentDocs` renders identically from the new source; a project with no Storybook still
has complete metadata.

### Group 2 — The relationship graph and consumption measurement

**Goal:** the layer VortSpec is missing outright, and the one that makes auditing possible.

- New `main/inspector/relationship-index.ts`, built on the existing B2 scan cache (do **not** shell out
  to the vendored Python skill — implement in TS, reuse `component-reader`, keep the Electron app
  dependency-free).
  - **Key every entry on the full project-relative path**, never the filename stem (§1.2).
  - Resolve imports per framework via the existing `FRAMEWORK_PROFILES` table so a new framework is
    covered automatically.
  - Emit `uses[]` / `usedBy[]` with recursive chain resolution.
  - Count **instances** by parsing component tags in template bodies, not imports; handle slots,
    conditionals and loops; de-duplicate slot-nested instances.
  - Compute per component: `importCount`, `instanceCount`, `efficiency = instances / importing files`.
  - Detect **shadow implementations**: markup that reproduces a component's structure without importing
    it. This is the finding designers care most about and it falls straight out of the graph plus the
    hardcoded-value scan already in `design-audit.ts`.
- Persist to `.vortspec/ai/index.toon`, `component-usage.toon`, `design-tokens.toon` (token → consuming
  components, the reverse index). TOON on disk; the in-prompt digest keeps its current compact format.
- Extend `buildIndexDigest` with a bounded relationship section, and add a `usedBy`/`uses` lookup the
  agent can request on demand rather than always paying for the full graph.
- Regenerate on the same triggers as the scan cache; stamp `generatedAt` and surface staleness.

*Verify:* run the four benchmark questions (§1.6) against a real project with and without the graph.

### Group 3 — Query protocols

**Goal:** teach the agent to navigate instead of explore. This is the cheapest group and the one the
benchmark attributes most of the gain to.

- Add `.vortspec/ai/rules/` — project-scoped, generated, referenced from the run's system prompt:
  - `metadata-schema.md` — the contract of Group 1
  - `atomic-hierarchy.md` — dependency direction, organism → molecule → atom selection order
  - `deep-tracing.md` — recursive `uses` traversal, category filtering
  - `load-once.md` — never re-read a relationship file already in context
- Wire the vendored skills for real: `ai-ds-composer` becomes the selection strategy for compose and
  light-page runs; `ai-component-metadata` becomes the generator behind Group 1's prompt.
- **Give the light path its brain.** In `buildLightPagePrompt`, alongside `designer.md`, hand the model
  the `aiHints.selectionCriteria`, `variants.purpose` and `antiPatterns` for the components in scope.
  Extend `LiteComponent` (`lite-manifest.ts`) with a compact `hints` block and serialize it into
  `designer.md`'s frontmatter — it stays framework-free, so `findFrameworkPointers` still passes.
- Replace `compose-run.ts:295`'s `.slice(0, 4000)` on `DESIGN.md` with the structured digest. Truncating
  prose at a byte boundary is the worst possible way to spend those tokens.

*Verify:* an assertion that a light-page run's prompt carries selection criteria for every
`data-component` it is allowed to use.

### Group 4 — Governance v2 and the audit reports

**Goal:** move from "does this token exist" to "is this token used with intent".

- Encode design decisions as machine-readable rules under `.vortspec/ai/governance/`:
  - **hierarchy** — foreground/background sequence; which text roles may take which foreground token
  - **elevation** — shadow scale coherent with surface size and z-order
  - **semantic color** — intent tokens (`danger`, `success`) never used decoratively
  - **typography composites** — family/size/weight/line-height applied as a unit, not piecemeal
- Extend `AuditFinding.kind` beyond `hardcoded-color | token-drift` with the intent kinds, keeping the
  existing severity model.
- Add `reports/adoption.md` and `reports/token-violations.md` under `.vortspec/ai/reports/`, generated
  from the Group 2 graph: utilization per component, unused components, shadow implementations,
  violations grouped by component. Surface both in the Inspector's Issues view.
- Cost discipline: these are report-generation runs. Route them to the cheapest model that holds the
  schema (Haiku, consistent with the existing verify/Apply routing) — the author's own runs cost ~$0.20.

*Verify:* on a fixture with a deliberately hierarchy-violating but syntactically valid token reference,
v1 passes and v2 flags it.

### Group 5 — AI-readiness as a product surface

**Goal:** make the ladder visible, and make the whole thing self-measuring.

- Compute a maturity level (§1.7) from what the index already knows: metadata coverage, token
  determinism, governance-rule count, relationship density, violation rate.
- Show it on the Design System screen next to the existing `design-system-readiness` signals, with the
  specific next action that raises the level.
- CI freshness hook: fail when the index is older than the component dir's last change — the gap the
  author flags as unbuilt in his own system.

### Sequencing and cost

Groups 1 → 2 → 3 are the critical path; 3 delivers most of the benchmark gain and is small once 1 and 2
land. 4 and 5 are independent and can follow in either order.

Net token cost per run should be roughly flat (§1.6): the digest grows by a bounded relationship
section, and the model stops paying to grep. Report generation is new spend, but it is off the
interactive path and belongs on the cheapest capable model.
